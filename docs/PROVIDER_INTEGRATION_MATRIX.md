## Shared Laya path

Providers reach one Hub-owned Laya runtime through the shared MCP service. No provider-specific Laya daemon or permission bridge is created. With `[laya].enabled=true`, active typed advisories can suggest model route, context budget, retrieval strategy, and pipeline next step behind deterministic gates. Pipeline next-step guidance is returned in canonical route metadata; `run_test` is offered only when deterministic impact analysis found tests, and high/critical risk enables `ask_human`. The advisory never runs tools or tests. Retrieval choices are restricted to available backends and mapped to the hybrid retrieval weights; deterministic routing and a 75% context floor remain authoritative. Pipeline-supplied retrieval baselines are validated against the `hybrid_context_default` method and their scoped evidence ID. For unresolved evidence gaps, providers can explicitly request typed `context_source` advice through `local_ai_coord(curate_dataset)` with aligned evidence provenance; the suggestion never fetches data or grants access. Explicit `subagent_budget` advice uses a server-bound deterministic baseline of `single_agent`; the model's decomposition suggestion is metadata only and never starts agents or bypasses normal delegation gates. Typed model-backed decisions use a pinned checkpoint, verified evidence, and deterministic baselines. Decision and eligibility telemetry carries a canonical `provider_label` alongside repository/task/session scope: active HTTP request identity takes priority, and provider-scoped `LOCAL_AI_AGENT` is used for stdio MCP calls with no active HTTP identity. Portable hook launchers give an explicit `--host` identity priority over inherited provider environment. Unknown HTTP identities remain `generic_mcp`; environment fallback does not override an active request identity. This is attribution metadata only; it does not authenticate a provider or grant permissions. Adapter capability reports expose each provider's native hook event inventory through `client_status`, alongside the broad hook-support category. The pinned revision is cached locally and all five configured SHA-256 digests were verified on 2026-11-24; model-backed inference and device-quality acceptance remain open. `models.allow_hf_downloads=true` is the shipped default; set it to `false` for cache-only operation. Training and rollout remain separately gated.

## Codex hook coverage boundary

Codex documents lifecycle events including `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `SubagentStart`, `SubagentStop`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `Stop`, `Interrupt`, `PreCompact`, `PostCompact`, `PreModelRequest`, and `PostModelRequest`. The plugin and project-local setup wire six useful events: session/prompt/subagent-start guidance, pre-tool checks, post-tool checks, and `PermissionRequest` for Bash/patch calls. PermissionRequest is deny-only for deterministic policy violations; otherwise it returns no decision, leaving Codex's normal approval prompt intact. No hook approves a request or captures prompt, response, model-request, or transcript content. Stop/interrupt/compaction/session-end events have no bounded Laya operation today; SubagentStop and model events expose content or continuation/diagnostic controls without a required capability. Codex still requires host review/trust for plugin hooks.

`setup-report.json.provider_integration` exposes separate `configured`, `installed`, `enabled`, `trust`, `connection`, and `runtime_verification` states. `configured` reflects the setup operation outcome; installation and enablement remain `not_observed_by_setup` until a host-specific probe exists, while connection and runtime verification remain `not_probed_by_setup`/`not_run`.

Provider setup warnings are attributed only to the provider identities named in the action, including all explicitly named providers for shared paths; unmatched messages stay in `agent_config_unattributed_manual_actions`. When a batch setup aborts, selected providers report `outcome_unknown_after_batch_error` instead of all being labeled failed. Per-provider manual actions affect only their own component states.

`tools/verify_agent_handshake.py` reports direct `local-ai` MCP entries as `HUB_ROUTE_CONFIGURED`, Codex/Claude plugin enablement as `PLUGIN_ENABLED_CONFIGURED`, and Antigravity/Cursor native manifests as `PLUGIN_MANIFEST_PRESENT`. These statuses prove only that config declares a route, enablement, or manifest presence; they do not prove plugin activation, host trust, process launch, connection, permissions, or a successful handshake. OpenCode plugin entries are also configuration observations. The optional Hub readiness probe remains opt-in.
