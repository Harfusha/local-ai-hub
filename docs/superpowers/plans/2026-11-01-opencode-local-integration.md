# OpenCode local integration implementation plan

**Goal:** Integrate a local OpenCode V2 coding workflow with Local AI Hub, preserving existing installations and enforcing the local-only boundary.

**Constraints:** The current GPU is an RTX 4060 with 8 GiB. Live 12/16 GiB acceptance and model selection remain pending the planned 5070 Ti upgrade. Existing uncommitted changes and user configuration must be preserved. No cloud fallback in local-only mode.

**Ollama observations:** The supervised process was observed with one loaded model, one parallel request, flash attention and `q8_0`; its global context-length variable was absent. The OpenAI-compatible API does not set the model context size; Ollama documents a model alias with `num_ctx` as one route, which still requires target-GPU measurement. Ollama can route cloud models via its loopback endpoint. Explicit cloud names now reject; the provider accepts only Ollama 0.34.0 and forces `:local`. An isolated real-server test rejected a renamed remote alias while its unsuffixed control reached a loopback-only fake remote. Server identity, concurrent server replacement, and arbitrary shell networking remain unfenced. Do not label the local-only boundary complete.

## Work sequence

- [ ] Audit the MCP-to-daemon call graph, background workers, inference entry points, and GPU ownership. Define a fail-closed client-specific policy that reaches backend execution, including nested and asynchronous work. Verify rejection of unknown inference paths and preservation of other clients.
  - The stdio MCP server forwards requests to a shared HTTP daemon. The daemon constructs its own Ollama runtime, scheduler and background GPU worker. Filtering the MCP tool list alone does not prevent indirect inference or independent background activity.
  - Existing persisted completion evaluation checks receipt ownership, evidence, freshness, mutation generation and project verification rules. The installed MCP action set does not expose `verify_completion`; a goal integration must use a supported, authenticated path to that evaluator and must not fabricate receipts.
  - The HTTP task-create path no longer schedules adaptive context warmup for `opencode-local`; a focused test preserves warmup for other clients. This closes only that implicit path and is not the deterministic-only mode. The running daemon has not been restarted for this change.
  - The `opencode-local` MCP process hides `local_ai_task` and `local_ai_work` and rejects direct calls to them. Stdio tests verify those tools remain available to the `codex` profile. This is a surface restriction only, not the backend inference boundary.
  - HTTP route/action allowlisting and a synchronous request-scoped Ollama/llama.cpp deny now cover a limited set of local-profile operations. Real HTTP tests exercise search, memory and task creation without generation and preserve Codex delegation. The profile label is caller-supplied, arbitrary spawned threads are not automatically bound, and independent background workers/GPU ownership are not covered; this is not full deterministic-only enforcement.
  - Scheduler submission also rejects a restricted request before queueing, so this submission cannot lose its restriction when dispatched to a worker thread. This does not cover work already moved to a separate thread before submission.
  - An experimental external reservation fences scheduler dispatch, idle unload and background acquisition while held. Its capability hash persists under the configured state directory; tests cover concurrency, corrupt or failed writes, and abrupt process exit. It is not wired to OpenCode, cannot confirm external inference termination, and must not be treated as GPU ownership proof. Power-loss durability, competing Hub processes, and safe operator recovery remain unverified.
  - An experimental single-model session wrapper serializes requests and relays bounded-parsed SSE. Only a complete `[DONE]` event followed by upstream EOF permits another request; disconnects and malformed streams retain the fence. An authenticated loopback HTTP bridge forwards streaming chat to a loopback backend; fake-server tests cover wrong credentials, wrong model, competing requests, backend failures and truncated responses. An isolated OpenCode 2.2.5 process used the bridge with a fake backend and cleanly released the fence. The Hub owns authenticated start/status/stop endpoints, derives the provider credential from a configured Hub token plus nonce, and shuts the service down before its scheduler. A mode change to gaming or maintenance requests shutdown and rejects the transition until stopped, with startup and transition sharing the existing mode guard. Setup activation, actual Ollama/GPU behavior, safe recovery and full GPU ownership remain unverified.
  - RAG search is now available through the existing lexical index for the local profile, without embedding, reranking or joining semantic singleflight. Real HTTP and indexed-store tests cover this fallback. Other RAG actions and semantic retrieval remain unavailable to this profile.
  - The existing deterministic caller lookup is also allowed for the local profile; an isolated HTTP test finds a real Python call without generation. This is not proof of Serena availability.
  - A bounded Hub `solve` request did not return before cancellation. During this audit `ollama ps` reported a 7B model loaded and the machine was running a game; ownership of that model load was not established. Do not infer GPU exclusivity from the MCP filter or run benchmark inference while another workload owns the GPU.

It disables project OpenCode config; an isolated adversarial-project probe saw neither endpoint override nor foreign plugin execution. A real OpenCode + isolated Hub + fake model test passed. Focused tests cover continuation, restart, deduplication, interruption and unknown mutation outcomes. Cross-process concurrency and a full real-session workflow remain unverified. Missing or mismatched binding blocks continuation and resume can retry the read-only check.
