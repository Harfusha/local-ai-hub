# T21 typed adapter contract and ownership handoff

This handoff records the isolated T21 core in worktree `t21-project-config`. It does not authorize edits to another task's files. `/api/context/pack` remains Agent 2-owned.

## Typed core contract

`resolve_project_config(root)` returns `ProjectConfigResolution`:

- `settings`: validated `ProjectSettings` for all T21 fields.
- `active_sources`: safe source labels only (`defaults`, `project`, `git_common`, `worktree`); never absolute paths.
- `error_codes`: machine-readable failure codes. Any malformed or invalid layer rejects the whole overlay and selects built-in defaults.
- `config_digest`: SHA-256 of canonical effective settings.
- `phase_is_allowed(settings, phase)`: true only for known optional phases not listed in `skip_phases`.

Direct `ProjectSettings` construction normalizes sequence inputs to tuples and freezes mappings recursively. `language_overrides` accepts JSON-compatible values only; TOML date/time values reject the overlay atomically.

Precedence: built-in defaults < root `.local-ai.toml` < `<git-common-dir>/info/local-ai.toml` < root `.local-ai.worktree.toml`. Map values merge recursively; lists replace; higher scalar wins. Common directory lookup uses one shell-free `git rev-parse --git-common-dir` call bounded to 1.5 seconds. No Git means project config plus defaults. Both root config files are readable by the resolver and excluded from normal file, pinned-context, and entry-point candidates so prompt/config contents do not flow through project retrieval.

`ProjectContext` carries resolved settings and the project-scoped hint store. `ProjectContext.prioritize_paths(..., path_hints=())` ranks the complete candidate set in this order: literal configured `entry_points`, request-scoped `path_hints`, then saved hints matching config digest, requested purpose/scope, and Git revision. `entry_points` remain the durable primary paths; request hints are never persisted implicitly. `PathHint` is distinct from command argument `paths` and repository `changed_paths`:

```text
PathHint(path, purpose, scope, evidence_id?, provenance?, repository_revision?, config_digest?, expires_at?)
```

The single optional wire field is `path_hints`, an array of records with required `path`, `purpose`, and `scope` strings and optional `evidence_id`, `provenance`, `repository_revision`, `config_digest`, and `expires_at` strings. Do not add a `paths` alias. Request hints may omit evidence metadata; persisted learned hints require evidence ID, provenance, current repository revision, current config digest, repo-relative literal path, and an existing contained target. The store keys by a hash of Git common directory plus optional `shared_namespace`; no full root path is stored. Different common directories cannot share hints.

Retention is bounded to 256 hints per purpose/scope/revision/config group and 4096 hints per project identity. Oldest rows are evicted first; other revisions remain available until project-wide cap is reached.

`prioritize_paths_with_hints(...)` returns every input candidate, reordered only. It rejects stale, missing, out-of-root, traversal, glob, and wrong-scope hints. `PathHintUsage` reports `hint_used`, `fallback_used`, and `hint_helped=None`; no consumer measures usefulness yet. Do not infer `hint_helped` from priority ordering. Its `paths` field preserves candidates and may contain absolute paths, so treat it as control data. `telemetry_metadata()` emits only the three named fields, keeps `hint_helped` unknown, normalizes the two usage flags, and never copies paths. Do not send the `PathHintUsage` object or hint paths to telemetry. Adapters must run a bounded broader fallback when priority pass has no useful result. Hints never make a complete result set narrower or grant path access. Consumers still call `path_is_allowed(...)` for every file and `may_descend(...)` for every directory; trusted route identity selects root. Hints never bypass excludes, hard-deny, binary, size, or trust boundaries and never change security scope.

`path_is_allowed(...)` and `may_descend(...)` fail closed for unknown phases; accepted path phases are `search`, `repository_search`, `preprocess`, `test`, and the optional phases `rag`, `call_graph`, and `modules`. They enforce root containment, worktree-override exclusion, hard-deny and binary boundaries, size cap, and preprocessing-only excludes. Each `exclude_paths` glob matches both the normalized repository-relative lexical alias and resolved target; either match denies the candidate before `path_overrides` or force includes. `path_overrides` are evaluated against alias and target; an exclude action wins conflicting decisions. `force_include_paths` overrides inherited standard ignore state only, never explicit project exclusions or hard-deny boundaries. On Windows, matching folds path separators and case; other platforms retain case-sensitive matching. If `max_file_size_bytes` is configured, missing size evidence denies the file. Globs match path segments: `*` and `?` stay within one segment; a segment exactly equal to `**` spans zero or more segments.

`path_overrides` maps repository-relative glob patterns to `include`, `exclude`, or `default`. Map entries inherit by key across config layers; higher layers replace identical pattern keys. Runtime chooses most-specific match: literal segments and characters rank first, then fewer `**` segments and wildcards. Equal-specificity ties deny. A winning `default` falls through to legacy force-include/soft-ignore/exclude behavior, including when it overrides a broader matching rule. Maximum 512 patterns.

Adapters walking directories must call `may_descend(...)` before pruning each directory. Pass inherited soft-ignore state and hard-deny state. A soft-ignored directory remains traversable when a force-include or path override `include`/`default` may match the directory or a descendant. Hard-deny and preprocessing excludes still stop traversal; force-include never overrides them. This lets ignored parents expose candidate descendants; each file remains subject to `path_is_allowed(...)`.

Command definitions are data only; resolver never runs them. Nested command env entries accept exact `${HOST_VARIABLE}` references only. Top-level `[env]` separates literal project values into `ProjectSettings.env` and exact references into `ProjectSettings.env_references`; partial interpolation rejects. Only an owning adapter resolves host references at command execution. Verification rules accept only `true` or a non-empty tuple of non-blank strings after normalization; `false`, empty lists, and malformed entries reject the overlay. Rule names/items remain data; evaluator semantics are owner-owned. `settings.commands` separately maps `_KEY` aliases to strings or `CommandDefinition(argv, description, env_references)`. `system_prompt_prefix` stays untrusted project context below system policy. Consumers must include `config_digest` and Git revision in affected cache keys. Telemetry may contain neither prompts/source/model output/secrets nor project or hint paths; emit only the three path-hint outcome booleans.

## Typed consumer contract

The trusted route or command owner resolves `ProjectContext` once with `resolve_project_context(root, state_dir)`. Keep `context.config_digest` with request cache identity. Pass the complete candidate set and typed `PathHint` records to `prioritize_paths_with_hints(...)`; hints may reorder, never filter or authorize. Before interpreting candidate content, call `custom_extension_kind(path, settings, language=...)` to honor configured text extensions. Before each file read, call `path_is_allowed(...)` with phase, hard-deny, ignore, and size evidence. Before each directory walk, call `may_descend(...)`. If priority order yields no useful result, run bounded broad fallback. Telemetry may use only `PathHintUsage.telemetry_metadata()`; `hint_helped` remains unknown until a consumer measures it. Never log candidate paths, hint contents, or raw `PathHintUsage`.
