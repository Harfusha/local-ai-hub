# Laya Active Decision Service, MCP/API, and Training Capture

**Operator steering (2026-11-12):** Use Laya where it improves reliability, quality, speed, or enables useful new behavior. Expose it through MCP/API. Collect useful local training data, including bounded raw content when it materially helps reproduce a training example. Review stays local: the operator can confirm labels, or a capable local Codex/model can review with explicit provenance. No remote reviewer keys, SSH quorum, or cloud fallback. Model review is not silently represented as human confirmation.

## Goal

Make Laya a shared, typed decision service inside Local AI Hub. Reuse the current app, scheduler, runtime, task/evidence authorization, state directory, telemetry, reporting, and candidate curation. Create no per-agent daemon. Deterministic Hub rules remain authoritative for permissions, receipts, task lifecycle, commands, and execution.

## Decision surfaces

Implement typed, category-specific proposals for context source/quality, context budget, model route, redundant work, next step/diagnosis, delegation/review, completion gaps, and watchdog recommendations. Survey additional Hub decision points when source evidence shows a useful gap. Each category has a deterministic baseline, shadow comparison, local review provenance, quality/latency/compute metrics, and its own activation gate. Keep categories shadow-only where no positive evidence exists. Advisory output cannot execute tools, grant permission, change task/receipt state, approve completion, or make a destructive decision. Filter route and operation options against server-verified availability. Abstention or failure preserves the baseline.

## MCP and HTTP

Expose a typed Laya decision request through an existing compact MCP tool and a root-authorized Hub HTTP API. Callers may select only a registered category and supply bounded input/evidence IDs. The server chooses mode, resolves repository/task/session identity, validates evidence and options, and applies category gates. Never accept caller-supplied identity, authorization, arbitrary tool execution, or a mode override. Direct API/MCP requests return explicit proposal, abstention, or unavailable status. API errors do not affect ordinary Hub behavior.

## Runtime lifecycle

Load Laya on its first request and retain the loaded session until 600 seconds of inactivity after the latest completed Laya request. Every later request resets the idle deadline; never unload while a request is in flight. Do not reject Laya solely because another model is loaded or a GPU reservation exists. Never evict, preempt, unload, or reconfigure another model. Preserve the configured hardware profile and CPU fallback. If actual provider or device capacity prevents Laya from loading, return an explicit isolated unavailable result and preserve deterministic Hub behavior. Use the existing Hub runtime; create no separate daemon.

## Training capture

Capture actual eligible Laya decision examples and useful outcomes: minimum raw request/context needed to reproduce the decision, authorized evidence/source references and hashes, deterministic baseline proposal, Laya output, subsequent accepted/rejected/overridden outcome where observable, review labels, model/runtime/provider identity, latency, token/compute metadata, and failures/abstentions. Store raw prompts, responses, and source excerpts only when they materially improve training value. For the current context-source pilot, pass the task query and relevant retrieved excerpts only; redact recognized credential/token/password patterns, bound each field to 8 KiB and combined raw content to 16 KiB. Record redacted and unavailable fields. Exclude unrelated private content and fields with no training purpose; do not store unrelated Hub conversations.

Automatic decision observations also attach to two server-owned callsites. The primary model-route observation is queued after ordinary `delegate` generation completes, only when routing was automatic and the request has an existing task plus current evidence IDs. Its baseline comes from the final `ModelRouter.classify` role; capture the typed task/complexity state and bounded task input. The repository context-budget observation is queued after successful retrieval and the delegated response, only when the caller did not choose an explicit token budget and retrieval supplied current evidence IDs. Its baseline comes from the configured fast/heavy context-token limit. Both use the existing bounded shadow queue and root/task/session validation; they never alter the route, token budget, prompt, response, or deterministic behavior. Missing scope/evidence or checkpoint skips capture. These are learning observations, not promoted decision policies.

Expose persisted runtime-output records through the existing root-authorized candidate operation as bounded, cursor-paginated `runtime_output_history`. Keep blind candidate `get` free of Laya outputs and labels; keep human-label training export separate from runtime-output history.

Deterministic baselines are derived by the Hub, never asserted by the caller. `context_source` records the authorized retrieval rank-order baseline. `completion_gap` records `ready` when the Agent OS completion gate passes and `not_ready` when it raises `CompletionGateError`; its evidence ID must be verified in the request and present in the current task checkpoint. Other gate failures propagate as failures, not as `not_ready`. Without a registered server baseline, candidate metadata stays `baseline.status=not_available` and cannot support paired evaluation.

Natural capture, storage, review, labeling, and export require no per-example consent, receipt, or separate per-example approval. Retired consent fields may be rejected but never gate these lifecycle stages. Preserve repository authorization, local access control, evidence provenance, deletion, and export safeguards.

Keep examples local under configured state storage, scoped to repository/task/session, revalidatable against current evidence, deletable with linked payloads and snapshots, and out of ordinary telemetry/logs/diagnostics. Preserve task/session/source group provenance to prevent split leakage. Record review kind, reviewer/model identity, exact local model and revision where applicable, prompt/rubric version, evidence, timestamp, confidence/abstention, and decision separately from the target. A model output is never represented as a human label. Human-confirmed labels and local-model-reviewed labels remain distinct in storage and export; a model review cannot silently enter a human-confirmed training export. The current source-label rubric is `laya-source-label-v1`: select only a permitted source that best resolves the gap using relevance, freshness, and coverage; do not invent evidence or treat Laya output as a label. The local operator may confirm a label, or a capable local Codex/model may provide a separately attributed review. No four-key SSH quorum or remote reviewer keys. Collect data now; do not start fine-tuning or publish data without a separate request.

## Rollout and verification

Keep each category shadow until paired comparison shows noninferior decision quality and measured improvement in reliability, quality, end-to-end latency, compute, or useful capability. Promote only a qualifying category to opt-in advisory; preserve a per-category off switch and deterministic fallback. Test MCP and HTTP contracts, identity and evidence authorization, redaction, capture scoping, deletion, dataset split, failure isolation, and concurrent lifecycle. Report source tests separately from installed live-model/provider evidence. Never claim device placement, quality, speedup, or memory release without direct measurements.
