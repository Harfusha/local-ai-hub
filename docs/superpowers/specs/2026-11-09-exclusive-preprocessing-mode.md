# Exclusive preprocessing activity mode

Add a fourth activity mode, `preprocessing`, alongside Active, Gaming and Maintenance. Its purpose is to spend available resources on preprocessing registered projects while temporarily preventing ordinary Hub requests from starting. Mode, status, health and the controls needed to leave the mode must remain available. Blocked calls receive an explicit retryable response; they are not silently lost or left waiting indefinitely.

Entering the mode must fence new foreground work and account for work already running before preprocessing claims its resources. Preserve existing GPU ownership, cancellation, authorization, project confinement, and failure handling. If a resource cannot be safely acquired, expose the wait or failure instead of reporting completion. Leaving the mode restores normal admission and normal resource limits without corrupting in-flight preprocessing.

Use profile-specific limits for project concurrency, CPU workers and preprocessing parallelism in both Active and Preprocessing modes. Double each profile's existing project, CPU-worker and preprocessing-parallelism values in both modes. Keep explicit user configuration overrides authoritative. Limits are bounded by actual resource and backend constraints; they are starting targets, not claims of measured optimal throughput. Preserve the configured preprocessing provider and all quality and cache correctness checks. Process the registered project set without forcing destructive cache invalidation or running optional diagnostics without approval.

In this mode, enrich existing `deterministic-stub` file cards with the configured preprocessing model when the file is within configured size limits. This overrides the ordinary-mode speed shortcut by default and can be disabled with `preprocessing.exclusive.enrich_stub_cards = false`. Keep each existing stub attached and usable until validated replacement is stored; do not delete cached data. A missing or failed model leaves enrichment pending rather than reporting it complete. Preserve deterministic cards with richer parser output, excluded paths, skipped phases and oversized-file limits. Model-generated summaries are not a guarantee of factual quality; report actual backend failures and validation limits.

Show the mode and progress in the existing dashboard activity control; support the existing mode API and CLI. Document behavior, configuration and retry semantics in the installation and update prompts. Tests must cover mode admission and exit, in-flight work and fencing, project scheduling, limit selection and restoration, failures, and existing modes. Runtime verification must distinguish actual measured throughput and completion from static tests.
