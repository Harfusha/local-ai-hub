# Laya Decision Service — Design

> Current status (2026-11-10): This is the initial design baseline. The current capture rules are in `2026-11-10-laya-candidate-capture-per-example-consent.md`. Ordinary eligible context calls can enqueue consented shadow capture, but runtime remains disabled by default; actual inference, provider placement, and device memory release remain unverified.

## Goal
Evaluate and, only where justified, add an optional typed-decision service around Laya Multilingual. Automatic use starts disabled or metadata-only shadow; explicit advisory calls remain estimates. Deterministic Hub rules, authorization, receipts, command broker and Agent OS state remain authoritative.

## Hardware portability target
Fine-tune one canonical multilingual checkpoint. Keep one shared ONNX graph as the default runtime export, with at most one additional precision-converted ONNX export if verified provider requirements demand it. Provider compilation caches are derived runtime artifacts, never separately fine-tuned variants. On Windows 11 24H2+, Windows ML may provide dynamic provider selection, but its current Python runtime API is experimental/pre-release; qualify it as an optional path and keep it inactive until it passes the Hub's runtime gates. For explicit provider paths, use CUDA for NVIDIA dGPUs; Intel OpenVINO for Intel CPU, iGPU, dGPU, and NPU; AMD Vitis AI/Ryzen AI software for AMD Ryzen NPUs; and DirectML for compatible AMD, Intel, or NVIDIA GPUs on Windows. AMD dGPU paths outside Windows require a currently supported provider such as MIGraphX on its supported platforms; do not rely on ONNX Runtime ROCm, which is deprecated/removed from current releases. No single provider covers every vendor's GPU and NPU. Detect registered providers and devices, select only compatible installed backends, and fall back to CPU. Provider availability does not establish that Laya's graph is supported or accelerated: validate operator coverage, actual graph placement, output parity, memory, and latency on each target. Precision conversion or quantization is a derived runtime artifact only when required, and must pass parity/quality checks before use. Record exact hardware, provider, driver/runtime, precision, and results; make no device support claim until that matrix is exercised on the actual model.

The Hub already ranks providers for retrieval/embedding acceleration (`src/local_ai_hub/accelerators.py`; `docs/INSTALLATION.md`). Reuse that hardware detection/provider-selection surface where its current implementation supports the target, but do not assume its ranking proves Laya inference support or graph placement. Laya provider candidates must follow currently maintained ONNX Runtime/vendor support; in particular, exclude deprecated ROCm paths.

Provider references (checked 2026-11-10): [ONNX Runtime execution providers](https://onnxruntime.ai/docs/execution-providers/), [Windows ML Python/runtime status](https://learn.microsoft.com/windows/ai/new-windows-ml/runtime/overview), [Windows ML provider deployment](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/distributing-your-app), [Intel OpenVINO](https://onnxruntime.ai/docs/execution-providers/OpenVINO-ExecutionProvider.html), [AMD Vitis AI](https://onnxruntime.ai/docs/execution-providers/Vitis-AI-ExecutionProvider.html), [AMD MIGraphX](https://onnxruntime.ai/docs/execution-providers/MIGraphX-ExecutionProvider.html), [AMD ROCm deprecation](https://onnxruntime.ai/docs/execution-providers/ROCm-ExecutionProvider.html), [Windows DirectML](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html), and [NVIDIA CUDA](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html).

## Architecture
Use existing Hub services, event/telemetry, task API, authorization, reporting and diagnostics ZIP. Add no orchestrator, event system, daemon, database, memory, or exporter. Internal callers use a shared service directly. Expose explicit advisory through an existing typed task action if clean; otherwise document why a new MCP/API surface is necessary. External input is closed decision category, permitted options and authorized evidence IDs. The server supplies mode and canonical task/session/repository identity; callers cannot set them or raise global mode. No transcript, source, private prompt, free-form authorization, tool execution or side effects. Model output is an untrusted proposal. Failure and abstention preserve the existing route.

## Stages
1. **Evidence/design:** inspect actual task, model routing/cache, Agent OS, telemetry/reporting, diagnostics ZIP and evaluation paths; verify upstream artifacts/revision/licence/tokenizer; select candidate categories only where a baseline and independent labels are feasible. Document blockers and exact boundaries. Current source map: `features.py` and `mcp_server.py:local_ai_task` own live task action enumeration/API; the action currently accepts broad text fields, so it is not a safe Laya contract by itself. `model_policy.py` owns configured model tiers; `semantic_cache.py` reuses semantic generations by model/system/options/context fingerprint and cannot directly key this new decision protocol. `app.py:export_diagnostics` calls the existing installation-wide encrypted ZIP in `diagnostics_export.py`; it is not project-filtered. `telemetry.py:summary/report` owns existing reports and aggregates; `benchmark.py` and `model_quality.py` provide existing evaluation/quality logic. `tests/test_model_quality.py` explicitly separates synthetic evaluator fixtures from live-model quality. Do not route changes through `config`, hardware/retrieval plans or dirty files owned by other work.
2. **Contract-only safe foundation (implemented, not exposed):** `src/local_ai_hub/laya_decisions.py` defines closed request/result enums, strict caller fields, server-bound mode and identity, allowed-choice checking, abstention, required reason codes for non-success and metadata-only projection. It loads no model and is not registered in MCP, HTTP, telemetry or ZIP; no behavior changes. Tests cover rejection, abstention, output validation and metadata projection. This is scaffolding only, not evidence of model value.
3. **One shadow category:** only after reproducible labeled fixtures and baseline exist. Disabled-by-default, nonblocking, bounded, metadata-only; explicit skips/fallbacks. Reuse existing event storage and reporting.
4. **Explicit advisory API:** only after contract and privacy review. Extend existing API/action. Cannot change global mode, invoke tools, or alter completion/permissions.
5. **Observability/export:** extend current report and authorized ZIP with metadata-only records, period/schema, provenance, eval summaries and included/skipped/missing manifest counts; preserve scope and limits.
6. **Evaluation gate/future:** compare paired cases to deterministic rules and independent labels, by category and Czech/English; count full request/schema/round-trip cost, latency and quality. Keep guarded use out of scope. Future advisory/guarded progression requires a separate evidence-based decision and opt-in.

## Contract option allowlists
The contract bounds choices by category. `abstain` is a status, never an option. Completion-gap choices cannot claim verification; watchdog values are explicitly recommendations; repeated-work values cannot skip validation. Route options are further filtered by server-verified availability. These labels are proposal enums, not commands or permission grants.

## Candidate decision contract

These templates are proposals only; no inference category is enabled. Choice IDs and order belong to the schema version. Build questions from server-owned templates. Abstention is a result status, never a choice. Never pass arbitrary caller instructions, transcripts, source, task titles, paths, or private text. A label must come from an independent reviewer or deterministic oracle that directly answers the question. User acceptance, Laya output, and task completion alone are not gold labels.

| Category | Trigger and minimum state | Typed question and closed choices | Label and useful outcome | Unacceptable false positive | Abstain and fallback |
|---|---|---|---|---|---|
| `context_source` | Evidence planner has an unresolved gap and multiple authorized sources. Pass source availability, freshness/coverage codes, and evidence IDs. | Choice: `indexed`, `artifact`, `memory`, `rag`, `more_evidence`. Ask which available source can close the named gap. | Frozen evidence gap plus independent adjudication of the source containing the required fact. Useful only if it removes a retrieval round without losing facts. | Selecting unauthorized, stale, or incomplete evidence. | Unknown coverage or tied sources: abstain; use deterministic retrieval order. |
| `context_budget` | Compiler has measured token counts and mandatory/optional section counts. No task prose. | Choice: `compact`, `standard`, `expanded`. Ask which configured profile fits the fixed limit and retains mandatory sections. | Deterministic compiler result plus held-out fact-retention review. Useful only if input cost falls with no mandatory fact loss. | Dropping goals, authorization, evidence, or verification requirements. | Missing counts/retention oracle: abstain; use configured compiler profile. |
| `model_route` | A route is needed and current tier quality gates exist. Pass task class, available tier IDs, and gate states. | Choice: `fast`, `smart`, `background`, `vision`, `generic`. Ask which already-qualified tier matches the task class. | Paired held-out evaluation against policy and independent labels. Useful only if quality stays above its floor and total cost or latency improves. | Choosing an unqualified tier or overriding explicit policy. | No passing quality evidence or policy conflict: abstain; keep configured route. |
| `redundant_step` | Request ledger finds a possible repeat. Pass action class, idempotency/cache state, revision, and evidence-freshness flags. | Choice: `possible_duplicate`, `validation_still_required`. Ask whether evidence indicates repetition while preserving validation obligations. | Exact request identity plus independent confirmation reuse preserves the same result. Useful only if it avoids a duplicate call. | Suppressing tests, verification, refreshed evidence, or non-idempotent commands. | Any identity/revision ambiguity: abstain; keep existing deduplication and cache rules. |
| `next_step` | Bounded operation failed, evidence is incomplete, or a blocker exists. Pass error/reason codes and evidence IDs only. | Choice: `inspect_source`, `run_test`, `retrieve_evidence`, `ask_human`. Ask which permitted evidence step should come next. | Independent review against the failure and later verified evidence. Useful only if recovery shortens without skipping checks. | Claiming a test ran, recommending an unauthorized command, or skipping validation. | Missing error identity or authorized evidence: abstain; use deterministic recovery guidance. |
| `delegation` | Bounded work is being considered. Pass task class, scope size, capability eligibility, and policy flags. | Choice: `review_only`, `delegate_bounded`, `no_delegation`. Ask whether review or already-authorized bounded work fits. | Independent human assessment against actual scope, permission, and quality gates. Useful only if unsuitable handoffs decrease. | Starting, authorizing, or routing work; architecture/security work cannot become bounded delegation. | Missing scope, permission, or quality result: abstain; retain direct ownership. |
| `completion_gap` | Agent OS receives completion request. Pass required criterion IDs and persisted receipt/status flags. | Choice: `missing_verification`, `resolve_blocker`, `request_human_review`. Ask which gap-handling hint applies; never attest completion. | Deterministic receipt validator is the reference. Laya adds no value absent a measured gap. | Inventing receipts or declaring completion from narrative/model output. | Missing/expired/ambiguous receipt: abstain; deterministic completion gate decides. Keep disabled by default. |
| `watchdog` | Heartbeat is stale or explicit stuck signal exists. Pass task status, elapsed-time bucket, retry count, and blocker codes only. | Choice: `recommend_continue`, `recommend_stop`, `recommend_human_review`. Ask for recommendation only. | Independent human adjudication of observed state and later resolution. Useful only as a shadow alert with measured precision and no intervention. | Automatic stop, forced continuation, cancellation, or permission change. | Unknown owner/state or conflicting signals: abstain; existing watchdog remains authoritative. Shadow only. |

Do not enable a category until its labels, deterministic baseline, privacy review, and per-category evaluation exist. `completion_gap` already has an authoritative receipt gate; omit it unless a concrete measured gap appears. Do not add calls where deterministic/cache evidence suffices.

## Safety and portability
No dependency/runtime/weight/driver downloads, cloud inference, daemon, automatic rollout or promotion. No hard-coded hardware. If hardware work is later authorized, report actual backend/provider/version/device and verified execution placement; otherwise NOT VERIFIED. Keep cache identity tied to category, model/config revision and authorized scope without raw text. Bound queue, concurrency, latency and memory; one fallback per backend at most. Shadow off means existing Hub path unchanged. No raw model payloads or private text in telemetry/export.
