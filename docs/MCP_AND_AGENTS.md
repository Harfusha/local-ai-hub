# MCP and coding-agent integration

Development and Git integration follow the [simplified worktree process](superpowers/specs/2026-10-07-simplified-worktree-integration.md): primary agent owns audits and integration, branches/worktrees are exceptional, small verified units return to `master` promptly, and leftover changes are classified before recoverable archival. No routine audit handoffs, ZIPs, owner packets, or custom fingerprint/hash cascades.

Local AI Hub exposes eight compact MCP tools instead of mirroring every internal endpoint. Target runtime has one user-scoped Hub daemon and lightweight stdio proxies; a proxy must not instantiate `InProcessTransport`, `HubServices`, or another `LocalAIApp`. This T03/T04/T13 integration remains pending in the current candidate. The daemon and service pools are shared across Codex, Claude Code, Gemini CLI, Cursor, Windsurf, VS Code/Copilot and generic MCP clients. Project-local MCP manifests use `target_root` as `cwd`; global manifests use `install_dir`. Every global repository, task, or memory request must set `root` to the caller's project root and preserve task context. Both MCP API and `HubClient` must pass root explicitly; never infer it from install cwd. The server derives effective tenant from principal and canonical root. Tenant headers/body/query values are optional consistency checks, not tenant selectors. T13 auth/lifecycle implementation is candidate-only and untested. Do not start a separate Hub daemon for each agent.

## Codex MCP configuration

Use the `local-ai` entry generated by setup; do not copy or hand-author a proxy command, arguments or environment. Project-local configuration is generated for `target_root`; the global Codex entry is generated with `cwd=install_dir`. Keep the generated working directory. For each global repository, task, or memory request, set `root` to the caller's project root and preserve task context; the global entry's process cwd identifies the Hub installation, not the repository. Pass caller `root` for repository targeting; current candidate does not validate roots against `allowed_roots` or derive tenant from root. HTTP uses tenant labels from `X-LocalAI-Tenant`, then `X-Tenant-ID`, then `http-default`; labels are not authorization. See [Security model](SECURITY_MODEL.md) for confirmed behavior and pending T13 scope.

The global Codex entry has `cwd=install_dir` and no project-root environment. Each active MCP session may spawn its own stdio adapter process; it forwards Hub calls through `HubClient` over HTTP and does not construct `LocalAIApp`, `HubServices`, `ProjectPreprocessor`, `CodeIndex`, `RAGStore`, or model pools. Per-session adapter count is not daemon count; inspect parent/command line and the single OS user-service identity. Repository-scoped repo/RAG MCP actions reject omitted or `.` roots at the adapter boundary; preprocessing rejects a missing absolute root. Always pass the caller's project root. This source-level guard still needs runtime/deployment proof.

The generated MCP, HTTP, client and CLI surface inventory with contract and evidence states is in [API surface coverage](API_COVERAGE.md).


## Optional whole-task orchestration

Use `local_ai_work` only when the user explicitly requests a closed task delegated to the Hub. Do not use it to hand off audits or the primary agent's repository ownership. The primary agent keeps the plan, reviews diffs, and integrates directly. If explicitly requested, `submit` may run a closed bounded task; use `status`/`wait` once for bounded progress, `cancel` to stop it, and `continue` only after a `needs_agent` decision.


## Hub-first evidence and cloud-agent autonomy

The primary agent plans, audits, implements, reviews, and integrates directly. Local-model calls are optional and advisory; use `local_ai_task` for bounded semantic reasoning or compression after deterministic/indexed evidence when it adds value. Generated text does not replace exact facts, symbols, diffs, or test evidence. Do not delegate audits. Native Codex subagents are only for genuinely independent bounded implementation or explicit user requests; keep scopes disjoint and integrate directly without a handoff bundle.

For every non-trivial repository task, agents should start preprocessing the stable absolute project root once with `local_ai_repo(action="preprocess", root=...)` and continue immediately. Preprocessing is opportunistic: never poll or wait for it.

Adoption gate: `local_ai_command` alone is not a repository workflow. After the one-time preprocess call, every non-trivial task must use the cheapest applicable non-command Hub action (`deterministic`, `code_index`, `search` or `context`) before running commands. For implementation, diagnosis, refactoring or complex review, call `local_ai_repo(action="solve")` after evidence and before native edits; after edits, use `impact`, `review_diff`, `security_audit` or `local_ai_artifact` as applicable.

Before native recursive search/tree/glob or opening many files for discovery, route repository evidence cheapest-first: `deterministic` -> `code_index`/`search` -> Serena `semantic` -> `context` / `solve`; use RAG only for missing bounded retrieval and use `local_ai_task` for semantic generation/reasoning/review after needed evidence. Stop as soon as the required evidence is available. Do not launch overlapping deterministic/search/context/RAG/model calls in parallel for one question; broader layers already compose or reuse cheaper indexes, so only independent questions should be parallelized. Repeatable tests, lint, typecheck, builds and safe read-only commands go through `local_ai_command`, which state-keys, caches and single-flights duplicate work.

When an agent uses `local_ai_repo(action="solve")` with explicit semantic wording such as explore, explain, why, compare or second opinion, the planner keeps one bounded local pass even if exact evidence is already strong. Pure fact lookups still terminate deterministically.

## Adaptive repository context

Use `local_ai_repo(action="context")` as the default adaptive context pack before non-trivial planning, edit, review or test. Pass the existing task/budget/workspace and guarded fields (`phase`, `focus`, `preload_profile`, `guarded`, `changed_paths`, `since_hash`, `approval`, `override_reason`); omit them to use the single canonical `adaptive` mode. Reuse existing evidence and reuse candidates first, require evidence IDs for factual claims, and treat deterministic/indexed evidence as authoritative. Local models may rank, select or compress structured evidence only; they may not invent repository facts. Scope or drift overrides require an explicit `override_reason` and approval when requested. Responses stay compact and omit raw model/debug fields unless requested through `extra_fields`.

When generation is needed, use `qwen2.5-coder:1.5b` for quick work, `qwen2.5-coder:3b` for ordinary work, `qwen2.5-coder:7b` for hard reasoning, and `qwen3.5:9b` for extreme reasoning in the balanced profile; reserve `qwen2.5-coder:0.5b` for preprocessing. Deterministic/indexed evidence still runs first.

Use `E…` evidence or artifact slices for exact source, and bounded native reads such as `view_file` for a known path and required slice. Keep recursive search, broad globs and command validation behind Hub-first retrieval and the bounded fallback rules. Fresh Hub discovery and command results should not be repeated natively. `force=true` and `preprocess_refresh` are exceptional controls, not retry mechanisms.

If Serena is unavailable, the hub degrades to built-in indexes. Treat response state as a protocol: cache/coalesced results should be reused; `in_progress=true` means another owner is doing identical work; HTTP 429/retryable 503 means back off and do independent work; degraded/stale evidence should trigger verification of only the affected path or evidence slice. A non-retryable failure permits one cheaper/native fallback. If the hub itself is unavailable, perform one bounded health/retry check and then use native tools; never loop on health, preprocessing, model startup or an optional backend, and never increase timeouts as a retry strategy.

## Public operation contract notes

- `local_ai_status.detail` uses `brief`, `cache`, `telemetry`, `full`, `agent_state`, or `traces`; `traces` accepts `min_duration_ms` and `trace_action`. `action` also accepts the `status`, `health`, `check`, and `info` aliases.
- `local_ai_repo(action="pipeline")` accepts closed step objects with a supported action and per-step `id`/`result`; run no more than four steps in parallel.
- `local_ai_artifact(action="list")` does not require `artifact_id`; `binary` is supported and binary payloads are never inlined.
- `local_ai_coord(action="pubsub_poll")` accepts `after_seq` from 0 through 2^63-1.

## RAG document and diagram ingestion

For `local_ai_rag(action="ingest_document")`, non-empty `content` is required; `title` and `metadata` are optional. Success returns `success`, `workspace`, `document_title`, `chunks_ingested`, and `embedded`. Embedding errors do not stop lexical publication. For `ingest_diagram`, `image_path` must resolve to an existing `.png`, `.jpg`, `.jpeg`, `.webp`, `.svg`, or `.bmp` file; `caption` and `metadata` are optional. Success also returns `diagram_indexed` and the resolved image path.

## Cloud-agent request and delivery contract

The canonical envelope is the existing JSON body plus `X-LocalAI-Tenant`, `X-LocalAI-Agent`, and one `X-LocalAI-Request-ID` per logical request. Reuse the returned result for `cache_hit` or `coalesced`; do not submit an equivalent foreground request again. A duplicate request ID briefly waits for its owner and replays its completed response when available; only then can it return `in_progress:true`. Replay-safe transport recovery is bounded to one retry with the same request ID, and overload responses carry `retryable:true` plus `retry_after_seconds`; wait at least that hint before any new attempt.

For model-backed `local_ai_task` actions, use `delivery="sync"` when the answer must be inline (the default), `delivery="async"` when the agent can continue independently, or `delivery="auto"` with a positive `latency_budget_ms`. Auto delivery submits the existing durable, coalesced background job only after at least ten observations show endpoint p95 over that budget; sparse history stays inline rather than guessing. Retrieve a submitted job with one bounded `wait`, then `result`; never poll.

Durable async actions: `batch`, `compress`, `delegate`, `reason`, `review`, `review_diff`, `route`, `second_opinion`, `speculative_lint`.

HTTP foreground delivery maps `/api/delegate`, `/api/reason`, `/api/review`, `/api/review/diff`, `/api/second-opinion`, `/api/compress`, `/api/route`, and `/api/delegate/batch` to their corresponding durable actions. Direct MCP `submit` uses `job_action` from the durable action list above. `sync` is the default delivery; `async` submits immediately on mapped HTTP routes.

For HTTP `/api/review/diff`, auto delivery first checks queue age: when `review.max_queue_age_ms` is positive and queue age exceeds it, the request returns a terminal 503 bypass. Otherwise, a positive `latency_budget_ms` with fewer than 5 telemetry samples selects async with reason `cold_start_review_diff`. Other auto delivery follows the measured p95 rule above.

Async lifecycle responses preserve `job_id`, `state`, `artifact_id` (empty until available), and `expires_at` (Unix timestamp seconds). Expiry is set at submission; terminal job results become `expired` at that time. `async_jobs.result_ttl_seconds` defaults to 259,200 seconds (72 hours), and artifact-store TTL must cover it. A timed-out wait returns current state with `wait_timeout_seconds` and does not cancel the job. Queued cancellation returns terminal `cancelled`; running cancellation returns `running` with `cancel_requested=true` as acknowledgement, then worker completion supplies final state.

Direct HTTP lifecycle requests use `POST /api/async-jobs`: submit sends `action="submit"`, `job_action`, and optional stable `request_id`; controls send `action="status"|"wait"|"result"|"cancel"` with `job_id`, and wait also sends `timeout_seconds`. MCP uses `local_ai_task(action=submit|status|wait|result|cancel, ...)`. `HubClient.submit_async_job`, `HubClient.async_job_status`, `HubClient.wait_async_job`, `HubClient.async_job_result`, and `HubClient.cancel_async_job` call the same HTTP path.

Recovery may replay only explicitly replay-safe actions with a stable `request_id`, matching tenant/action/payload identity, and remaining attempts; command-backed and unclassified actions become terminal `outcome_unknown` after interruption.

### Conversation lifecycle

Initial and continued task text must be nonblank.

Start synchronously with HTTP `POST /api/delegate` or `POST /api/reason`, setting `conversation=true` and `delivery="sync"`, or MCP `local_ai_task(action="delegate"|"explore"|"reason", conversation=true, delivery="sync")`. `HubClient` has no dedicated start helper; use `post("/api/delegate", payload)` or `post("/api/reason", payload)`. Continue with HTTP `POST /api/conversations/continue` and body `conversation_id`, `task`, optional `context`; MCP uses `local_ai_task(action="continue", conversation_id=..., task=..., context=...)`; `HubClient.continue_conversation(conversation_id, prompt, context=...)` maps `prompt` to HTTP `task`. IDs are opaque and tenant-scoped. The initial model, system prompt, output limit, temperature, and route stay pinned for the conversation. Only one turn can be active; a concurrent continuation returns retryable in-progress status.

Conversations allow up to 12 user turns by default. The prompt limit comes from `model_conversations.max_prompt_tokens`, falling back to `token_saving.max_local_input_tokens` or 56,000 tokens. Defaults are 900 seconds idle TTL, 1,800 seconds active TTL, and capacity 1,000. Conversation state and transcripts remain in process memory and are lost on restart.

Repository context uses the single canonical `adaptive` mode, with bounded deterministic/indexed retrieval and optional semantic backends. It does not run an open-ended generation task. Repository responses expose `cache_hit`, `cache_layer="workspace"`, and `coalesced`; reuse them instead of submitting a near-identical root/revision/query request.

Root-fingerprint repo cache, request coalescing, optional Serena circuit cooldowns, and `evaluation_record` / `evaluation_report` are already shared across agents. Use opaque task IDs and cohorts for paired baseline/candidate quality, test-pass, and duration evidence; never put source or prompts into evaluation metadata. Ordinary requests may attach `evaluation: {"task_id":"opaque-id","cohort":"hub_on|hub_off","quality_pass":true,"test_pass":true}`; the hub records its measured duration automatically. Pairing still requires the corresponding other cohort. CodeGraphContext/KuzuDB are not called or managed by the Hub.

The built-in client reuses HTTP/1.1 loopback connections per thread and coalesces simultaneous identical active requests. A coalesced response has `coalesced:true`; reuse it rather than creating another request. `in_progress:true` is not an operational failure: honor its retry hint or continue independent work. Git-only `review_diff`/`impact` calls on a non-Git root are terminal client results; switch to deterministic/code-index review rather than retrying Git.

The client also rejects an empty code symbol before transport. Command `classify`/`discover` must precede unfamiliar commands; a policy or executable preflight rejection is terminal and should never be retried.

For an honest deployment cohort, use `/api/metrics?scope=process` or `/api/telemetry/report?scope=process`. This excludes persisted pre-restart history and reports per-agent request count, failure rate, p95 and p99 without retaining prompts, source, or model output. The default `scope=window` remains the rolling-history view.

`evaluation_report` includes a report-only promotion gate. It requires ten matched `hub_on`/`hub_off` opaque task IDs, complete quality and test evidence, no regression, and lower hub-on average duration. `promote` is evidence for an operator rollout, never an automatic routing change.

## Agent configuration

Setup preserves unrelated user configuration and can install MCP entries for Codex, Claude, Gemini, Antigravity, Cursor, Windsurf and VS Code/Copilot. Antigravity's global manifest is `~/.gemini/config/mcp_config.json`; setup keeps its `local-ai` entry aligned with the Gemini profile and removes stale direct Serena entries when direct MCP is disabled. Portable generated manifests intentionally contain the Hub-only `local-ai` entry by default; direct Serena remains opt-in via `code_intelligence.direct_agent_mcp`. `[agents].extra_mcp_json_paths` / `extra_vscode_mcp_paths` can write explicitly requested custom host configs. The `local-ai-orchestrator` skill and MCP tool descriptions intentionally repeat the same policy so hosts that do not load external skill files still receive the routing contract.

For concurrent agents, use `local_ai_coord` leases before overlapping edits and memos for reusable findings.

## Ollama advisory profiles

Named profiles are available through existing `local_ai_task` and `local_ai_repo` tools: `qwen-explorer` for reconnaissance and bounded interpretation, `qwen-drafter` for proposed implementation guidance, and `qwen-critic` for independent review. With a repository `root`, each profile uses Hub read-only tooling directly, in order: preprocessing/deterministic facts, code index, optional Serena, search/RAG, evidence IDs, then bounded file slices. Profiles never write files, run commands, create worktrees, or apply proposals. Default model is `qwen2.5-coder:7b`; output mirrors task language and preserves technical tokens. Use `qwen-explorer` when the task needs semantic interpretation or exploration; skip named profiles only for pure exact facts already covered by deterministic/indexed tools. CodeGraphContext is optional standalone tooling configured directly with an agent, not a Hub dependency, runtime, or backend. Hub profiles do not install, manage, search, or query it.

## Synthesis scope

`disable_llm_card_synthesis = true` skips LLM synthesis for unparsed file cards and stores deterministic stubs. It does not disable module/project cards: `prefer_deterministic_modules` and `prefer_deterministic_project` are separate preferences, and either path can use background LLM synthesis when deterministic output is unavailable or below its confidence threshold. Check active configuration and backend state before claiming synthesis is disabled.

## Local model conversations

Start a synchronous conversation with `local_ai_task(action="delegate"|"reason", conversation=true, ...)`. The response returns an opaque `conversation_id`; continue it with `local_ai_task(action="continue", conversation_id=..., task="...")`. A conversation pins its initial model, route and system instructions, accepts one active turn, and is bound to its server-derived effective tenant.

Conversation history is process-memory only: it expires after inactivity and disappears after a hub restart. It bypasses generation, semantic and artifact caches, so no transcript or continuation output becomes durable cache state. Profiles and async/auto delivery are unsupported for conversations. Omit `conversation=true` to retain normal stateless behavior.

## Agent Operating System projection
 
When `[agent_state].enabled` is active, the compact MCP surface projects durable agent operating system state without adding new tools:
- `local_ai_coord`: `task_create`, `task_get`, `task_checkpoint`, `task_transition`, `task_resume`, `task_list`, `task_complete`, `task_fail`, `ask`, `answer`, `memory_record`, `memory_get`, `memory_find`, `memory_promote`, `context_compile`, `verify_receipt`, `verify_completion`, `negative_knowledge_record`, `negative_knowledge_find`, `incident_decision`.
- `local_ai_repo`: `context_compile`, `verify_receipt`, `verify_completion`.
- `local_ai_task`: `candidate_create`, `candidate_promote`.
- `local_ai_status`: `detail="agent_state"` for health and counts.
- `ask` stores only explicitly submitted question text under the request-bound root, tenant, and session; retrieve with same scope and `question_id`. `answer` stores operator response under the same root and tenant. Tenant authentication requires the existing configured-principal/security policy; a tenant label alone is not proof of identity. Do not put credentials in questions or answers.
- Privacy boundary: telemetry remains metadata-only; question and answer text is durable local Agent OS state, separate from telemetry.
## Shared workspace memo contract

Treat workspace memos and leases as trusted-local shared coordination state; tenant labels are caller-supplied provenance, not identity or authorization. Workspace memos are keyed by canonical workspace and key. Use `expected_version` from a memo read when `memo_put` must reject stale overwrites; a `version_conflict` returns the current generation, so reread and reconcile before retrying. Omission retains last-writer-wins; deletion advances the generation while expiration does not.

## Aggregate response budgets

Every public Hub tool now applies an aggregate agent-facing response budget after semantic projection. Default is approximately 3200 tokens. Use `max_response_tokens` for a bounded override; explicit values below 128 are rejected, never silently increased. Use `response_profile="minimal"|"compact"|"standard"|"debug"|"delta"` for intent, and a stable `reuse_key` for repeated logical queries. `delta` returns changed fields only; unchanged repeated results return a pointer envelope with IDs and summary instead of repeating payload data. Independent local-model work uses the existing `local_ai_task(action="batch")` path.

Telemetry records operation category plus raw/projected/saved response estimates, budget truncation, cache outcome, and projection reason. The bounded context ledger is visible only through an explicit `local_ai_status(detail="cache")` request and stores metadata only: no prompts, source text, secrets, or full paths. Hub command execution already caps captured/inline stdout and stderr; intercepting native Codex host `exec` requires a separate host hook and is not silently emulated by MCP.

The installed user hook at `.cursor/hooks.json` blocks broad native `cat`/`type`/`Get-Content`/`rg`/`grep`/`tree` reads without an explicit bound. It fails open on hook errors. Use `-m`, `-First`, `head`, `local_ai_repo`, or `local_ai_artifact` when exact detail is needed.

## Document and diagram ingestion

- Document ingestion requires nonempty `content`; `title` and `metadata` are optional. Success returns `success: true`, `workspace`, `document_title`, `chunks_ingested`, and `embedded` (`true` when at least one chunk has an embedding).
- Diagram ingestion requires an existing `image_path` with a supported `.png`, `.jpg`, `.jpeg`, `.webp`, `.svg`, or `.bmp` extension; `caption` and `metadata` are optional. Success adds `diagram_indexed` and the resolved `image_path`.
- Embedding failures do not stop lexical publication; chunks without embeddings remain searchable lexically. These ingestion methods do not return `embedding_status`, `ingest_publish_failed`, or a `retryable` flag.

## LLM card synthesis scope

`disable_llm_card_synthesis` applies to fallback synthesis for unparsed file cards only. Module and project cards use separate `prefer_deterministic_modules` and `prefer_deterministic_project` settings; background LLM synthesis may still run when deterministic card generation does not satisfy its acceptance conditions.
