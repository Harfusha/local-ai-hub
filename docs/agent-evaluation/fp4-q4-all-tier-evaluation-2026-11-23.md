# All-tier FP4 vs Q4 Evaluation

**Status:** In progress; seven model-size comparisons were measured on CUDA: Qwen3.5 9B, Qwen3-VL 4B and Qwen2.5-Coder 0.5B/1.5B/3B/7B/14B. The 14B comparison is provisional because neither checkpoint exposes an exact shared upstream commit. MiniCPM-V source requires user agreement to share contact information; conditional 32B exceeds host VRAM.

## Scope and Method

Evaluation covers unique model families/sizes and every tier role that points to them: preprocessing, background/subagents, fast/heavy code, reasoning, general and vision. Shared model-role entries are tested once. Exact Q4 artifacts are compared with same-base FP4 where an appropriate checkpoint/runtime exists. A speed figure across different runtimes is not attributed to quantization alone.

The authoritative CUDA runs use the same official llama.cpp `b12649` Windows CUDA 13.5 build, RTX 5070 Ti, context 4096, `temperature=0`, `top_p=1`, seed 42, and no-thinking mode. Performance generation is the median of three repeats. The Qwen3.5 pair comes from Ollama's Q4_K_M and NVFP4 GGUF artifacts; Ollama reports both as Qwen3.5 9B Base from `https://huggingface.co/Qwen/Qwen3.5-9B-Base`, but does not expose the exact upstream commit in model metadata. Qwen3-VL's NVFP4 card declares the Instruct base but not its exact base revision; its Q4 reference was generated from the locally pinned HF revision `ebb281ec70b05090aa6165b016eac8ec08e71b17`. These are same-family/base-name comparisons, not commit-proven identical source weights.

Qwen2.5-Coder 0.5B, 1.5B, 3B and 7B use local `Qwen/Qwen2.5-Coder-*-Instruct` snapshots pinned respectively to commits `ea3f2471cf1b1f0db85067f1ef93848e38e88c25`, `2e1fd397ee46e1388853d2af2c993145b0f1098a`, `488639f1ff808d1d3d0ba301aef8c11461451ec5` and `c03e6d358207e414f1eca0bb1891e29f1db0e242`. NVIDIA ModelOpt 0.48.0 generated each NVFP4 checkpoint with the same 128 synthetic code calibration prompts (SHA-256 `a02355a650f6d75feae698ec91efb75b518043c7911326cf2de301bccaf73598`), then official llama.cpp converted the checkpoint. For every pair, Q4_K_M was independently generated from that same pinned BF16 snapshot. Thus these four coder pairs share exact base revisions; Transformers was 5.24.0, which ModelOpt warns is untested.

An earlier run happened before CUDA runtime DLLs were beside `llama-server`; `--list-devices` then showed no CUDA device, so its CPU performance numbers are excluded. The reported timings below come only from the later run where `--list-devices` confirmed CUDA0 and the model loaded on the RTX 5070 Ti.

NF4 is tracked separately from FP4: it is a 4-bit lookup-codebook quantization, not an IEEE-style FP4 encoding and not NVFP4. CUDA libraries can provide GPU kernels for NF4 operations, but that does not establish use of Blackwell's native FP4 Tensor Core path. [bitsandbytes NF4 implementation](https://github.com/bitsandbytes-foundation/bitsandbytes/blob/main/bitsandbytes/functional.py), [NVIDIA NVFP4 format and hardware documentation](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/nvfp4/nvfp4.html)

## Runtime Constraints Found

- The Windows Transformers dynamic `NVFP4Config` kernel path failed because `kernels-community/nvfp4-gemm` has no matching Windows build. NVIDIA ModelOpt 0.48.0 did quantize, export and run Qwen2.5-Coder 0.5B/1.5B/3B/7B on Windows; the four Q4 comparators and NVFP4 results all used official llama.cpp b12649 CUDA 13.5 on the RTX 5070 Ti. Installed Transformers is 5.24.0, which ModelOpt warns is outside its tested versions, so these successful measurements are exploratory, not a qualified installation route. NVIDIA's current deployment matrix lists generic Qwen 2.5 NVFP4 support as experimental (`⚠`) for TensorRT-LLM/vLLM and unsupported in SGLang; this does not itself establish Windows or llama.cpp product compatibility. [NVIDIA ModelOpt deployment matrix](https://github.com/NVIDIA/Model-Optimizer/blob/main/docs/source/deployment/3_unified_hf.rst#L258-L303)
- WSL2 reported `Wsl/Service/E_UNEXPECTED` for a shell launch.
- A temporary Linux CUDA Docker probe failed during startup: `libnvidia-ml.so.1` was unavailable in the container runtime. No Docker GPU workload was launched.
- Official llama.cpp source supports GGUF NVFP4 conversion/loading for pre-quantized ModelOpt/compressed-tensors checkpoints. It cannot synthesize NVFP4 from ordinary BF16 by `llama-quantize`; conversion requires an already-NVFP4 checkpoint.
- For Blackwell W4A4 verification, llama.cpp was run once with the documented `GGML_CUDA_MMQ_PREC=q4` override; the default `auto` run was also retained. Qwen3-VL NVFP4 did not beat same-runtime Q4 in this small set. Qwen3.5 NVFP4 was modestly faster while tied on these eight checks. Neither result alone qualifies a broad route change.
- Qwen2.5-Coder 14B ModelOpt low-memory loading on 0.6 GPU budget ended before export; 0.4 GPU budget moved layers to CPU, then Accelerate failed when moving a packed ModelOpt quantized tensor back to `meta`. This is a host/runtime blocker, not evidence that NVFP4 is unsupported by Blackwell hardware.
- A separately published 14B NVFP4 checkpoint was converted and measured with llama.cpp, yielding a provisional same-family comparison above. Its source commit remains unreported, so the run does not qualify a strict quantization-only result or product route.
- A 32B repository found by name search labels its quantization inconsistently: title says NVFP4 while model card says INT4 weight-only. It is excluded pending verifiable NVFP4 metadata and a host that can load the pair.

## FP4 Preference Record

**Provisional preference: `qwen3.5:9b-nvfp4` only.** Among the measured artifacts, it is the sole candidate with a clear throughput win over its Q4 counterpart: +7.6% in `auto` mode and +7.9% with the W4A4 override, while both scored 8/8 on the small quality set. This is a speed preference, not a quality win. Do not mark the other tested NVFP4 artifacts as preferred: Qwen3-VL and Qwen2.5-Coder 0.5B/1.5B/3B were slower; 7B's sub-1.5% speed edge came with one fewer passed case; the provisional 14B candidate was 8.7% slower. Qwen3.5's exact upstream revisions are not exposed, so this artifact-level preference remains provisional. The static catalog selects it only on Windows AMD64 with detected native FP4 and the default `auto` provider. Setup adds that selected tag to the existing Ollama model-pull list; the existing pull opt-in still controls downloads. This does not qualify other providers, platforms, architectures or models.
